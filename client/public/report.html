ABSTRACT

Electronic financial platforms represent the vanguard of modern digital commerce but frequently suffer from critical vulnerabilities including uncoordinated state updates, lack of double-entry ledger bookkeeping, race conditions during simultaneous transfers, and vulnerable flat schemas susceptible to SQL injection and uncoordinated updates. This academic project presents the design and implementation of the "DIGITAL WALLET MANAGEMENT SYSTEM" (WalletWise), a secure, full-stack, and user-centric platform tailored for collegiate and organizational financial simulation under the tagline "Your Digital Wallet, Smarter & Safer".

The architecture bridges a normalized relational Database Management System (3NF schema using SQLite3 / MySQL) with an atomic transaction engine enforcing ACID (Atomicity, Consistency, Isolation, and Durability) guarantees. Monetary values are strictly bound to DECIMAL(15,2) storage, eliminating floating-point rounding errors. Peer-to-peer transfers execute under deterministic numerical wallet-id lock sequences, eliminating cyclic deadlock risks, while an isolated double-entry ledger table (transaction_entries) records balanced CREDIT and DEBIT entries for every completed financial event.

Furthermore, the project delivers an advanced user experience featuring a high-contrast White/Light Mode interface by default (with instant Dark Mode toggling) and an integrated WiseVoice AI Voice Assistant powered by the browser Web Speech API capable of hands-free speech recognition (STT) and voice response synthesis (TTS) for balance inquiries, deposits, transfers, and utility bill settlements.

The system was rigorously evaluated through an automated test suite verifying Bcrypt authentication, unique email and wallet constraints, atomic transfer rollback, bill settlements, and parameterized query defense against SQL injection with 100% test passage in 143ms.

Keywords: Relational DBMS, 3NF Normalization, ACID Transactions, Double-Entry Ledger, Deadlock Prevention, AI Voice Assistant, Light Mode UI, Parameterized Queries.

Chapter 1: Introduction

CHAPTER 1: INTRODUCTION

1.1 Background of Digital Payment Systems

Democratic and transparent commercial interaction fundamentally relies on the ability of individuals and institutions to transfer value freely, securely, and accurately. Over the last three decades, currency management has steadily migrated from cash ledgers and physical plastic cards toward electronic wallet architectures. Digital wallet platforms streamline everyday financial interactions by consolidating multiple bank instruments, payment balances, and utility clearing services into a unified client interface.

1.2 Problems with Conventional Wallet Systems

Conventional computerized wallet solutions exhibit significant systemic drawbacks: (1) Uncoordinated State Updates: Flat schemas and improper transaction boundaries permit race conditions where rapid simultaneous debit requests cause overdrafts and double-spending; (2) Absence of Double-Entry Accounting: Simple prototypes frequently log single transaction records without balanced debit and credit entries, rendering mathematical auditing impossible; (3) Denormalized Database Structures: Storing provider or recipient metadata redundantly results in update anomalies; and (4) Vulnerability to SQL Injection: Concatenating client-supplied parameters exposes financial tables to unauthorized data extraction.

1.3 Introduction to WalletWise Architecture

WalletWise addresses these foundational challenges by integrating a strict relational DBMS (SQLite3 / MySQL) with an atomic transaction engine. By enforcing Write-Ahead Logging (WAL), foreign key cascading rules, and check constraints on decimal balances, every monetary event is executed with guaranteed mathematical consistency. In this project, peer-to-peer transfers, deposits, and utility bill settlements are decoupled into structured relational entities and audited via double-entry ledger bookkeeping.

The motivation for this project stems from the need for a practical, highly visual, robust, and accessible digital wallet platform designed for college DBMS laboratory evaluations and academic coursework. Chapter 2: Literature Review

CHAPTER 2: LITERATURE REVIEW

2.1 Conventional Electronic Wallet Systems

Silberschatz et al. [1] and Elmasri & Navathe [2] analyzed concurrency control anomalies in transactional database engines. Early banking systems frequently suffered from uncoordinated client updates where simultaneous withdrawals against the same ledger produced lost update anomalies. In digital wallet engines, isolation levels must ensure serialization of debit operations to prevent overdraft states.

2.2 Relational Database Systems and ACID Guarantees

ACID properties (Atomicity, Consistency, Isolation, Durability) constitute the bedrock of electronic financial transactions. Applying database-level transaction blocks ensures that deducting funds from a sender wallet and crediting a recipient wallet occur as a singular atomic unit. If any step fails—such as a recipient wallet being frozen or a database constraint violation—the entire operation rolls back automatically, preserving consistency.

2.3 Concurrency Control and Deadlock Prevention

Deadlocks arise when two concurrent transactions attempt to lock the same set of resources in reverse order (e.g., Transfer A: Wallet 1 -> Wallet 2; Transfer B: Wallet 2 -> Wallet 1). To eliminate this vulnerability, the system enforces a deterministic ascending lock acquisition order based on numerical wallet IDs (min(id1, id2) followed by max(id1, id2)), ensuring acyclic wait-for graphs.

2.4 Double-Entry Ledger Bookkeeping

Modern accounting standards require that every debit is balanced by an equivalent credit. By implementing a dedicated transaction_entries sub-ledger, the application ensures that total system credits strictly match total system debits, facilitating mathematical auditability and discrepancy detection.

2.5 Secure Authentication and Role-Based Access Control (RBAC)

Ferraiolo and Kuhn [4] established Role-Based Access Control (RBAC), formalizing how permissions are granted based on assigned roles (USER vs ADMIN). Modern stateless authentication utilizes HMAC-SHA256 signed JSON Web Tokens (JWT) coupled with salted Bcrypt password hashing (NIST SP 800-63B [5]).

8.1 Password and Credential Protection

Passwords are never persisted in plaintext. Bcrypt with 10 salt rounds generates 60-character salted digests, preventing dictionary and rainbow table attacks.

8.2 Session Handling and Authorization

HMAC-SHA256 signed JWT tokens authenticate user requests. Role-based guard middleware protects administrative routes from unauthorized access.

8.3 SQL Injection Prevention

All database interactions use parameterized SQL statements via db.prepare(?). User inputs are strictly treated as data literals, neutralizing SQL injection vectors.

8.4 Duplicate-Transfer Prevention & Double-Spending Protection

Strict ACID isolation combined with database-level uniqueness constraints guarantees that users cannot double-spend their available balance.

8.5 Double-Entry Ledger Reconciliation

Every transaction generates balancing credit and debit rows in transaction_entries, ensuring mathematical balance reconciliation.
